# i18n — Interface and AI Response Languages

Lare Terminal supports three languages: **Italian** (default and ultimate fallback), **English**,
**Spanish**. This support spans two distinct concerns kept strictly separate at code level despite
normally sharing the same configuration value: the **interface language** (strings for windows,
menus, dialog messages) and the **AI response language** during conversational turns. These are two
separate mechanisms — static dictionaries on one side, an appended directive within the system
prompt on the other — each worth understanding in turn.

## Interface dictionaries

Each language has a flat key→string JSON file, all sharing the exact same set of keys in alphabetical
order — located during development/testing in `Test Run/Configuration/i18n/{it,en,es}.json`, though
the production path is always `<config_dir>/i18n/<lang>.json`, where `<config_dir>` follows the
resolution rule described in [`01-architecture.md`](./01-architecture.md). Keys are dot-namespaced
by area (`aichat.btn_admit`, `config.title`, `library.window_title`...) and may contain placeholders
in `{name}` style (e.g. `"{peer} è comparso in rete — entrare nella stanza con lui?"`), replaced at
runtime with concrete values.

Loading on the Tauri side (`crates/ui/src-tauri/src/i18n.rs`) is deliberately infallible:

- `load_dict(path)` parses a JSON file into a `HashMap<String, String>`. Missing file → empty
  dictionary, silent (first run, or language not yet installed). IO error or corrupt JSON → empty
  dictionary plus a warning log (`tracing::warn!`) — never an error aborting window creation.
- `load_merged_dict(i18n_dir, lang)` constructs the effective dictionary: begins with `it.json` as
  base, then — if `lang` is not `"it"` — overrides with keys present in `<lang>.json`. This provides
  an immediate fallback chain: a key absent in the requested language but present in Italian does not
  disappear; it remains in Italian.
- `t_sync(i18n_dir, lang, key)` translates a single key traversing the full chain `<lang>.json` →
  `it.json` → the literal key itself if unfound in both. This function is used on the Rust side to
  translate **native window titles** (text displayed in the OS window titlebar, outside the DOM):
  `config.title`, `library.window_title`, `aichat.window_title`, `note.window_title`,
  `plugin.window_title`, `routine_preview.window_title_save`/`_update`, `screener_picker.window_title`,
  `search.window_title` are all resolved this way when the window is spawned — not reactively if the
  language changes while that window is already open.

The Tauri command exposed to the frontend is `get_i18n(lang) -> HashMap<String, String>`
(`crates/ui/src-tauri/src/main.rs`), returning `load_merged_dict` for the requested language.

On the frontend, `crates/ui/frontend/i18n.mjs` holds an in-memory dictionary providing:

- `t(key, params)`: translates a literal key with optional interpolation (`{name}` style), returning
  the raw key if absent — **only literal string keys** must be passed to `t()` in application code,
  never dynamically constructed keys (this constraint enables static extraction used by the parity test
  below).
- `fetchI18n(invoke, lang)`: calls `get_i18n` via Tauri IPC and initializes the in-memory dictionary;
  infallible for callers (catches errors, preserving previous state).
- `applyI18n(root)`: walks the DOM of a given container (default `document`) and applies translations
  across four attribute types: `data-i18n` (textContent), `data-i18n-placeholder`, `data-i18n-title`,
  `data-i18n-aria-label`.

Every window in the application (terminal, `/config`, Library, AI Chat, Notepad, external channels,
search dialogs...) follows the same lifecycle on startup: reads configuration via `get_config`, uses
`cfg.language` to call `fetchI18n`, then calls `applyI18n()`. Language switching is also **hot**:
the configuration window emits a Tauri event `config:saved` with `payload.language` on save; every
open window listens for it and re-runs `fetchI18n` + `applyI18n` without restarting the application —
applying to DOM contents, though not affecting already set native OS titlebars (which update upon
next window creation).

## The parity test: guaranteeing dictionaries do not drift

`crates/ui/frontend/i18n-parity.test.mjs` is the single gate preventing the three dictionaries from
drifting out of sync, operating generically (it does not hardcode `it`/`en`/`es` — it dynamically
scans all `*.json` files present in `Test Run/Configuration/i18n/`, using `it.json` as baseline). It
enforces three properties via distinct assertions:

1. **Key parity across dictionaries**: every file other than `it.json` must possess the exact same
   set of keys as `it.json` — missing keys or extraneous keys compared to Italian fail the test,
   listing diverging keys in the assertion message.
2. **No orphan keys in code**: every key actually *used* in code — extracted via regex from
   `t("key")`/`t('key')` and `data-i18n*="key"` in frontend `.html`/`.js`/`.mjs` files (excluding
   `vendor/` and test files), plus `t_sync(..., ..., "key")` in production Rust code under
   `crates/ui/src-tauri/src` (text truncated at `#[cfg(test)]` markers so test-only keys do not
   count) — must exist in `it.json`.
3. **No dead keys in the dictionary**: the inverse — every key defined in `it.json` must actually be
   referenced somewhere in scanned code. A dictionary cannot accumulate translations for keys no
   longer called anywhere.

An honest technical detail: the Rust code scan only covers `crates/ui/src-tauri/src` (the Tauri side).
Strings used elsewhere — AI language directives in `crates/orchestrator`, window titles for `/help`,
the safety string in `crates/orchestrator/src/help.rs` — do not route through this dictionary and
are therefore not covered by this test: they are hand-maintained Rust constants for each supported
language (see sections below).

## The special case: `/help`

The body text of the `/help` command does not live as a string in Rust code, but in external Markdown
files per language: `<config_dir>/help/<lang>.md` (in test environments:
`Test Run/Configuration/help/{it,en,es}.md`). The module `crates/orchestrator/src/help.rs` explicitly
defines its single responsibility — localizing and loading that content — with a three-tier fallback
chain:

```
load_help_body(help_dir, lang):
  <lang>.md  (if readable)
  → otherwise it.md  (if readable)
  → otherwise "Aiuto non disponibile: file mancante."  (minimal safety string, always in Italian)
```

It never panics or bubbles IO errors to callers — even if `it.md` is missing, the user still sees
content, never a broken `/help` window. The top comment in the file explains why this was externalized:
avoiding continuous growth of `core.rs` with increasingly long Rust constants as languages are added.

However, the **window title** for `/help` remains a Rust constant in `crates/orchestrator/src/core.rs`
(`HELP_TITLE_IT`, `HELP_TITLE_EN`, `HELP_TITLE_SPANISH` — respectively "Lare — Comandi", "Lare —
Commands", "Lare — Comandos"), resolved via a `match` against the request language. This same
`match` normalizes requested languages to a recognized code (`"it"` if neither `"en"` nor `"es"`)
**before** passing it to `load_help_body`: the fallback chain in `help.rs` is reached only with codes
already recognized by `core.rs`. In practice: dropping a `Configuration/help/fr.md` file without
adding a corresponding match arm in `core.rs` has zero effect — the file is never inspected, because
requests for "fr" collapse to "it" one step earlier.

## How language reaches the AI prompt

The mechanism for AI responses is independent of interface dictionaries: it flows through a command
message field propagating across the entire channel → orchestrator → system prompt chain.

- The protocol (`crates/protocol/src/lib.rs`) adds a `lang: String` field with `#[serde(default)]` to
  `ClientMsg::Command`: clients omitting it receive an empty string rather than deserialization
  errors — an additive field designed for backwards compatibility.
- If the field arrives empty, the orchestrator falls back to globally configured language:
  `shell_slash::read_language(config_dir)` reads the `language` field of `config.json` (defaulting
  to `"it"` if missing). This fallback is explicitly applied in `crates/orchestrator/src/shell_turn.rs`
  (`run_ai_turn`) and `crates/orchestrator/src/ws.rs`.
- The resulting value populates `agent::TurnOptions.lang: Option<String>`, and
  `agent::system_prompt(opts)` (`crates/orchestrator/src/agent.rs`) inspects it to append a final
  directive to the base prompt:

  ```rust
  pub const RESPOND_ITALIAN: &str = " Rispondi in italiano, in modo conciso.";
  pub const RESPOND_ENGLISH: &str = " Answer in English, concisely.";
  pub const RESPOND_SPANISH: &str = " Responde en español, de forma concisa.";
  ```

  mapping `Some("en") => RESPOND_ENGLISH`, `Some("es") => RESPOND_SPANISH`, and all other cases
  (`None`, empty string, `"it"`, or unrecognized code) → `RESPOND_ITALIAN`. The phrase is written
  in the target language itself rather than translated from Italian — consistent with being the final
  token sequence read by the model before generating its response.

The foundational system prompt (`BASE_SYSTEM_PROMPT`, detailing available tools — `run_in_session`,
`open_target`, `show_markdown`, saved routines, active web search) remains written in Italian
regardless of selected language: only the trailing directive shifts language. This is a pragmatic
choice, not an inconsistency: models readily understand instructions written in one language while
generating responses in another, and it is the trailing directive — not tool descriptions — that
governs the actual language of the output.

## Channels that do not follow this directive

Not all channels adhere to the language directive just described, stemming from two architecturally
distinct reasons worth distinguishing rather than lumping together as generic exceptions:

**Channels with fixed system prompts (`system_prompt_override`).** `TurnOptions` features a
`system_prompt_override: Option<&'static str>` field which, when present, causes
`agent::system_prompt()` to return that text **immediately** — the language `match` is never
reached. This mechanism powers channels registered in `crates/orchestrator/src/external_channel.rs`
(`EXTERNAL_TOOL_CHANNELS`): network diagnostics `"netsec"` (triggered by `/netsec`, prompt
`NMAP_SYSTEM_PROMPT`, terminating explicitly with hardcoded "Rispondi in italiano, in modo conciso."),
alongside `"library-expand"`, `"python-ping"` (`/pyping`), and `"financial-markets"` (`/markets`).
Each carries a scoped toolset (never generic `run_in_session`/`open_target`) and a dedicated prompt
describing those tools: output language today remains whatever was hardcoded into that channel's
prompt, irrespective of user configuration.

**AI Chat: a separate pipeline, not an exception in the same mechanism.** AI Chat (the cross-machine
shared chat room, independent of the terminal) does not route through `respond()` /
`system_prompt()` / `TurnOptions` at all — it maintains dedicated methods on `AiAdapter`,
`chat_reply` (answering explicit `@ai` invocations) and `chat_autoparticipate` (autonomous
contribution, Slice 2), each with custom prompt builders (`chat_system_prompt`, `autoparticipate_system_prompt`
in `crates/orchestrator/src/ai_adapter.rs`). These dynamically construct AI instance identity (name,
provider) but conclude with a static instruction — "rispondi SOLO con testo semplice, in italiano" —
hardcoded in Italian without any reference to `lang`. Thus it is not a channel *ignoring* the
directive: it is a completely separate AI entry point that simply does not know about it.

**Telegram: neither — remains in Italian by omission, not architecture.** Honestly noted because it
is less clear-cut than it appears: Telegram channel code
(`crates/orchestrator/src/telegram/channel.rs`) explicitly sets `system_prompt_override: None`
(comment in code: "Telegram non ha un concetto di canale, resta sempre `agent::SYSTEM_PROMPT`"
[Telegram has no concept of channel, remains always `agent::SYSTEM_PROMPT`]) and
`lang: None` (comment: "Telegram non passa `lang`, usa il default (italiano)" [Telegram does not
pass `lang`, uses default (Italian)]). Telegram therefore
**traverses the exact standard mechanism** of the local terminal — it has no custom prompt — but in
its current implementation never forwards a user-selected language, meaning the `match` in
`system_prompt()` always falls through to the default Italian arm. This is a subtle but genuine
difference compared to `netsec`/`library-expand`/AI Chat: in those, language selection is
structurally unreachable (prompt is fixed before the match, or the match does not exist); on
Telegram, the mechanism is present and standard, but no value other than "absent" is ever dispatched
from that channel today.

## Changing language

Language is selected from a dropdown in the configuration window (`/config`,
`crates/ui/frontend/config-dialog.js`), offering three fixed options: "Italiano", "English", "Español".
Menu labels **are deliberately not translated** based on currently active language — remaining
fixed so that a user who accidentally selects an unfamiliar language can still recognize their native
language in the list to switch back. The chosen value is written to the `language` field of
`config.json` (defaulting to `"it"` if absent), the same source read both by frontend initialization
fallbacks on window spawn and orchestrator fallbacks when clients omit language on AI turns: in daily
usage, "interface language" and "AI response language" reflect the same configuration value, even
though — as shown above — their underlying enforcement mechanisms remain independent in code.

## Adding a new language, step by step

The codebase contains at least **four points** where supported languages are hardcoded (there is no
single central registry): missing even one leaves the new language silently broken — no errors,
no crashes, simply remaining in Italian or omitting the dropdown option. In order of modification:

1. **`crates/orchestrator/src/agent.rs`** — add a `RESPOND_<LANG>` constant (the directive written
   in the target language itself, matching the concise tone of existing directives) and a
   `Some("<code\>") => RESPOND_<LANG>` arm in `system_prompt()`. Without this, the AI continues
   replying in Italian even when the user selects the new language.
2. **`crates/orchestrator/src/core.rs`** — add a `HELP_TITLE_<LANG>` constant and a matching match
   arm selecting title and `lang_code` for `/help`. Without this, the language code collapses to
   `"it"` before inspecting Markdown files — meaning even if the file exists, it will never be loaded.
3. **`Test Run/Configuration/i18n/<code\>.json`** (or production `<config_dir>/i18n/`) — the
   interface dictionary, providing full translations for **all** keys in `it.json` (verify the exact
   count by reading the file at implementation time — it has grown over time). Rules observed in
   existing dictionaries: keys in alphabetical order; all `{name}` placeholders preserved exactly
   (same name, only the surrounding text should be translated); product name "Lare Terminal" remains literal;
   natural, concise phrasing rather than literal machine translation.
4. **`Configuration/help/<code\>.md`** — the `/help` markdown body for the new language.
   Technically optional (fallback in `help.rs` yields `it.md`), but without it `/help` displays
   Italian text — it is not a true localization until this file exists.
5. **`crates/ui/frontend/config-dialog.js`** — an additional `<option>` in the dropdown, with a fixed,
   untranslated label in the native name of the language (following "Italiano"/"English").
6. **Parity test** (`crates/ui/frontend/i18n-parity.test.mjs`) **requires no modifications**: it
   dynamically scans all `*.json` files in `i18n/`, picking up the new dictionary automatically — if
   incomplete relative to `it.json`, the test explicitly lists missing keys.

`crates/protocol` requires no changes (the `lang` field is an unconstrained string). Recommended
verification: `cargo build`, `cargo test` on touched crates, `node --test crates/ui/frontend/*.test.mjs`
(must pass, including parity check on the new file), and `cargo clippy --all-targets`.

## Known limitations

To be explicit about what the system **does not** yet cover:

- Parity testing covers only `crates/ui` (interface dictionaries). Language constants on the
  `crates/orchestrator` side — `RESPOND_*` directives, `HELP_TITLE_*` titles, the `help.rs` safety
  string — are maintained manually without automated tests verifying coverage across supported
  languages.
- Channels with fixed prompts (network diagnostics, other registered external channels, AI Chat) currently
  answer only in Italian regardless of configured language — language is not (yet) exposed as a
  parameter on those paths.
- Telegram never forwards non-default language: even if added in the future, the underlying mechanism
  (`system_prompt()`/`TurnOptions.lang`) is already wired to accept it, lacking any hardcoded prompt
  override.
