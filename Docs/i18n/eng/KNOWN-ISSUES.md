# Known Issues — Lare Terminal 2.0

Two families of known issues: those **inherited from v1** (sections below; no Plan 1/2a tasks
touched these subsystems) and those **native to 2.0**, introduced by design decisions in the current
plan (marked accordingly). For the historical log of v1 issues (including resolved ones), see

[repository of the previous version](https://github.com/mauriziolobello/lare-terminal).

## [PARTIAL] Codepage — Output of NATIVE commands (`ipconfig`, …) → accented characters as `S`

**Reported:** Live by user in v1, 2026-06-26 (`ipconfig /all` → "Configurazione automatica abilitata : S",
where `Sì` was expected).

**Status in 2.0**:
- **Resolved in `crates/mcp-nmap` 2.0.1** (`local_network_info`/`traceroute` in `network_info.rs`):
  stdout/stderr output of native Win32 commands is now decoded by querying the console output code
  page (`GetConsoleOutputCP()`) or the system OEM code page (`GetOEMCP()` for windowless processes
  under `CREATE_NO_WINDOW`) via the `oem_cp` crate (`decode_oem`).
- **Still open in `crates/mcp-server/src/session.rs`** (Telegram / AI Chat channels): code copied
  from v1 was not altered (out of scope for the `mcp-nmap` task). In that session, output mingles
  PowerShell-generated text (UTF-8) with native Win32 output (OEM), requiring a line-by-line strategy
  or ConPTY.

**Symptom.** Accented characters in the output of **native Win32 commands** (`ipconfig`, etc.) appear
as U+FFFD (``) when executed inside the `mcp-server` session. PowerShell's *own* output (`Write-Output`)
is correct.

**Cause.** `crates/mcp-server/src/session.rs` injects `[Console]::OutputEncoding = UTF8` +
`$OutputEncoding = UTF8` into the session: this covers text *generated by PowerShell*, but **native**
commands directly inspect the console code page (`GetConsoleOutputCP`) and emit bytes in the **OEM**
code page (CP850/437), subsequently decoded as UTF-8 → mojibake. Invoking `chcp 65001` would resolve
this, but emits "Active code page: 65001" to stdout, corrupting the marker protocol — which is why
it was not applied in v1.

**Relevance to Plan 2/3.** In 2.0, the user interacts with the real shell via `lare-shell` (custom C#
PowerShell engine host, ADR-015/016), rather than the managed session of `mcp-server` — which remains
solely for channels without a local user shell (Telegram, AI Chat, see `CLAUDE.md`). The problem
therefore shifts: for local users, we must verify whether ConPTY (which forwards raw process bytes
rather than text re-decoded by `mcp-server`) exhibits the same symptom or avoids it by design — to
be verified when Plan 2/3 implements that path. For Telegram/AI Chat, the architectural problem
remains identical to v1.

## [RESOLVED] Infinite reconnect on permanently broken external channel

**Reported:** As architectural technical debt in v1 (`Docs/STATO-ATTUALE.md` §16: "a permanent
failure in an external channel (missing config/venv) causes infinite reconnect loops rather than an
error presented once").

**Resolved in `crates/ui` 2.3.3**:
- `crates/ui/frontend/ws-client.js`: introduced optional per-instance `maxRetries` parameter in
  `LareWsClient`. When consecutive attempts reach `maxRetries`, the client ceases timer scheduling
  and emits the terminal state `"failed"`.
- `crates/ui/frontend/external-channel-window.js`: passes `maxRetries: 6` (~31s total backoff before
  halting). `renderer.js` renders the terminal state with a localized badge (`ext_channel.status_failed`).
- **Important architectural note:** the primary window connection (`host.js`, cursor channel)
  **deliberately** retains infinite retry (no `maxRetries` passed). This constraint guarantees that
  the cursor UI automatically reconnects if the orchestrator restarts (rebuild, crash, self-healing),
  even after minutes, without leaving the user stranded with a frozen interface.
- Concurrently fixed the premature reset of `_retryMs` on the TCP `"open"` event, moving it to
  actual receipt of `server_info` (application-level handshake).

## [OPEN] Output window Markdown: transparency chunks and AI text concatenated without separator

**Introduced in Plan 2a** (native to 2.0, not inherited from v1): `surface::route_shell_turn` buffers
every `ServerMsg::Chunk` of a shell turn (AI transparency messages — "running `dir`…" — and actual
response text) concatenating them into a single `String`, delivered once to the window as
`OutputWindowContent` upon `Done`/`Error`. No separator (double newline, horizontal rule, etc.) is
inserted between consecutive chunks.

**Symptom.** If the AI outputs multi-line transparency text followed by response text, both can merge
into the same rendered Markdown paragraph (e.g. the last line of transparency and first line of the
response fuse into a single paragraph) — purely cosmetic, as all informative content remains intact
and readable.

**Relevance to Plan 2b/3.** Zero functional impact: does not impede reading or saving content to the
Library. To be addressed when output window rendering is revisited (alongside token-by-token
streaming, deferred past MVP — spec §12).

## [OPEN] Native technical debt of `lare-shell` host (Plan 2b)

- **`[Y/n]` gate accepted by pending keystrokes (observed ONCE, not reproduced).** In the initial live
  e2e run with a real AI, the first two turn gates appeared pre-accepted and the third `y` leaked into
  the subsequent prompt: duplicate/pending keystrokes in the console buffer (Windows Terminal + ConPTY,
  SendKeys driver). Mitigation in `ConsoleGate.Ask`: buffer is flushed PRIOR to the prompt (gate
  responds only to keys pressed afterwards), and discarded keys are logged (`gate: scartato tasto
  pendente …`, `gate: input mode …`). Subsequent runs exhibited zero pending keys. If it recurs, logs
  identify what was in the buffer.

**Introduced in Plan 2b** (native to 2.0): a deliberate design decision in the C# host (plan rulings,
ADR-019), not an accidental defect. Full implementation details in `shell/lare-shell/IMPLEMENTATION.md`
§Debiti (the source file is Italian-only); summarized here as user-observable symptoms.

- **AllUsers profiles not loaded.** `ProfileLoader` loads only CurrentUser profiles (`profile.ps1`,
  `Microsoft.PowerShell_profile.ps1`, `LareShell_profile.ps1`); AllUsers profiles (located in pwsh's
  `$PSHOME`, shared across all machine users) are not loaded. If critical session configurations
  reside there (rare: most customizations — aliases, oh-my-posh, modules — live in CurrentUser), they
  will not be present in Lare.
- **Host log lacks rotation.** `<config-dir>\logs\lare-shell.log` grows unbounded without daily
  rotation (unlike the orchestrator log) — plan ruling 7, declared technical debt: the spec (§6.2)
  calls for a 7-day file rotation.
- **`$?` in prompt after a slash turn.** Manually typed commands are never modified by a `/…` turn
  (ruling 3: only commands executed ON BEHALF OF the AI inside `ExecInShell` are wrapped in
  `try { … } finally { $global:__lare_ok = $? }`) — therefore `$?` at prompt level continues to
  reflect the user's last typed command rather than the recently concluded turn: a prompt or
  oh-my-posh theme reading `$?` right after `/ai` sees command status from BEFORE the `/ai` invocation,
  not a reflection of the turn.
- **`ui.exe` spawned by `lare-shell` with `UseShellExecute=true`, hidden window.** If after a
  self-heal invocation (`Launcher.EnsureUi()`) `ui.exe` windows (Markdown, `/config`, `/library`) do
  not immediately take foreground focus, this is standard Windows focus behavior for
  a process launched by another process (no forced `SetForegroundWindow`) — **not a bug**: the window exists
  and is visible; it simply requires selection (Alt+Tab or taskbar click).
- **`ToolConfirmRequest` lacks `turn_id`.** The `ToolConfirmRequest` message (v1) carries an opaque
  `id`, not the shell channel's `turn_id`: during a turn, `SlashTurn` attributes EVERY received
  confirmation request to the active turn (contract (a): single concurrent turn per connection,
  avoiding practical ambiguity), discarding any stale queue remnants from closed turns at the start
  of each turn.
- **On startup, `EnsureConnected` can block for up to ~8 s (3 s connect + retry) with Ctrl+C acting
  as no-op.** Occurs only if a service listens on port 7331 without responding (unlike the common
  case of "no listener", which fails immediately, or a live orchestrator responding within that window).
  The `Console.CancelKeyPress` handler IS already attached (registered prior to `ConnectAtStartup`)
  and FIRES on Ctrl+C — but has nothing to cancel: `_turnCts` is `null` (no slash turn active) and
  `Executor.StopCurrent()` has no active pipeline, meaning its only effect is a log entry ("Ctrl+C
  ricevuto (turno in corso: False)", F2a) while the connect/retry loop completes its timeout.
